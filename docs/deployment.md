# Deployment

## What is verified and what is not

| | Status |
|-|--------|
| Production images (compiled API as non-root, nginx-served SPA) | Built and run locally |
| Migrations as a separate release step | Verified locally (`docker-compose.prod.yml`) |
| Same-origin `/api` proxy incl. WebSockets, cookies, security headers | Verified locally: all 5 Playwright flows pass against it |
| Demo account seed (idempotent, in the production image) | Verified locally |
| `render.yaml` Blueprint | **Written but never applied to a real Render account** |
| HTTPS, secure cookies over real TLS, real client IPs behind the platform edge | **Not verified** — needs a real deployment |

Nothing has been deployed. Deploying needs your hosting account and real secrets, so those steps are yours.

## Architecture

```
browser ──https──▶ planner-web (nginx)  ── /            → static SPA (index.html fallback)
                                         └─ /api/*  ──▶ planner-api (Express, private)
                                                          ├─ Postgres (managed)
                                                          └─ Redis    (managed)
```

The browser only talks to one origin. This matters: the auth cookie is `Secure; HttpOnly; SameSite=Lax`,
and two subdomains of a hosting provider's shared domain (e.g. `a.onrender.com` and `b.onrender.com`) are
*cross-site*, so a Lax cookie set by the API would never be sent back from the web app. Proxying `/api` through
the web origin avoids that without needing a custom domain.

## Rehearse locally first

```bash
JWT_SECRET=$(node -e "console.log(require('crypto').randomBytes(32).toString('hex'))") \
POSTGRES_PASSWORD=choose-one \
docker compose -f docker-compose.prod.yml up -d --build      # http://localhost:8080
cd web && E2E_BASE_URL=http://localhost:8080 npm run e2e      # needs RATE_LIMIT_REGISTER=100 on the api for repeat runs
docker compose -f docker-compose.prod.yml down -v
```

## Environment variables (API)

| Variable | Production value |
|----------|------------------|
| `NODE_ENV` | `production` (the API refuses to start in production with the default `JWT_SECRET`) |
| `DATABASE_URL` | managed Postgres URL (use `?sslmode=require` if the provider's external URL needs TLS) |
| `REDIS_URL` | managed Redis URL |
| `JWT_SECRET` | long random value, generated by the platform or `openssl rand -hex 32`; never committed |
| `WEB_ORIGIN` | the **public** web origin, e.g. `https://planner-web.onrender.com` (CORS and WebSocket Origin allow-list; comma-separate to allow several) |
| `TRUST_PROXY` | number of proxy hops in front of the API (see below) |
| `LOG_LEVEL` | `info` |
| `RATE_LIMIT_GLOBAL` / `RATE_LIMIT_REGISTER` | optional; defaults 600/min and 10/hour per IP |

Web: `API_UPSTREAM` = `host:port` of the API on the private network (runtime). The build uses
`VITE_API_URL=/api` by default.

### `TRUST_PROXY` — get this right

Rate limiting keys on the client IP. Behind proxies that is only correct if Express trusts exactly the right
number of hops: too low and every user shares the proxy's IP (one user's failed logins lock everyone out), too
high and clients can spoof their IP via `X-Forwarded-For`. On Render the chain is *edge → nginx (web) → API*,
which is why `render.yaml` uses `2`. **After the first deploy, verify it:** call the API a few times from your
own machine, then check that the `ip` field in the API's request logs is your public IP, not an internal one
(and not a spoofable value), and adjust.

## Deploying on Render (Blueprint)

1. The repository is already on GitHub (`MillyDzukou/Collaborative-Project-Planner`, public) with CI passing; Render deploys from there.
2. Render dashboard → **New → Blueprint** → select the repo. Review the services it proposes from
   `render.yaml` (Postgres, Redis, private API, public web), and the plans/costs.
3. Apply. The first deploy builds both images; the API's **pre-deploy command** (`npm run migrate:up`)
   applies migrations before the new version takes traffic.
4. Set `WEB_ORIGIN` on `planner-api` to the web service's public URL (`https://…onrender.com`) and redeploy the API.
5. Open the web URL, register, create a project, open it in two browsers and confirm live updates.

### Seed the demo account (one-off)

In the API service's **Shell** on Render:

```bash
DEMO_PASSWORD='a-long-unique-password' node dist/db/seedDemo.js
```

Creates `demo@planner.example` (override with `DEMO_EMAIL`) with a sample 11-task network (17-week critical
path). Re-running is a no-op. To demo your own network (e.g. the coursework one), edit `NETWORK` in
`api/src/db/seedDemo.ts`.

### Other hosts

The images are host-agnostic: any platform that runs two containers plus managed Postgres/Redis works. You need
(a) the API reachable from the web container as `API_UPSTREAM`, (b) migrations run as a release step
(`npm run migrate:up` in the API image), (c) the env vars above, (d) HTTPS terminated by the platform.

## Release checklist

- [ ] `JWT_SECRET` is generated and unique; no secrets in git (`git grep -i secret` shows only code/docs).
- [ ] `WEB_ORIGIN` is exactly the public origin (scheme + host, no trailing slash).
- [ ] `TRUST_PROXY` verified against real client IPs.
- [ ] Register → login → create project → two-browser live update works over HTTPS.
- [ ] Database backups enabled on the managed Postgres plan.
- [ ] Demo account seeded; its password is not reused anywhere.

## Known limitations

- A single API instance has been tested; with more instances, WebSockets and fan-out go through Redis as designed
  (`docker compose --profile scale`), but it has not been load tested on a real host.
- The index migration builds inside a transaction (see `load/README.md`); on a very large table prefer
  `CREATE INDEX CONCURRENTLY` outside a transaction.
- No automated deploy pipeline yet (CI runs tests only); deploys are triggered by the platform on push.
